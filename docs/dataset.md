# Набір даних

## Запис пілотного набору

Учасники позначаються лише псевдонімами (P01, P02, …), запис без письмової згоди скрипт не
запускає. Цільові обличчя для атак – обличчя учасників за згодою або синтетичні. Записи
зберігаються лише зашифрованими (розділ «Шифрування записів»), тому перед записом треба задати
ключ у `PAD_DATASET_KEY`.

1. Реєстрація учасника: запустити запис і натиснути `E`, ембединг збережеться зашифрованим у
   `data/enrolled/P01.npy.enc`.
2. Справжні подання (наприклад, 10 сеансів, кожен починається клавішею `S`):
   ```bash
   python scripts/record_session.py --participant P01 --consent --type bona_fide --claimed P01
   ```
3. Атаки: у Deep-Live-Cam або DeepFaceLive вибрати цільове обличчя T01, вивести результат у
   OBS Studio і ввімкнути віртуальну камеру. Заявлена особа – ціль, тому її ембединг береться з
   фото цілі або з раніше збереженого `data/enrolled/T01.npy.enc` (не натискати `E` на підміненому потоці):
   ```bash
   python scripts/record_session.py --participant P01 --consent --type attack --tool deep_live_cam --target T01 --claimed T01 --enroll-image targets/T01.jpg --camera 1
   ```
   Індекс віртуальної камери залежить від системи (зазвичай 1 або 2).
4. Додатково можна вказати умови: `--lighting low --webcam-model "Logitech C270"`.

Кожен сеанс зберігається в `data/recordings/<псевдонім>_<тип>_<час>/`: `video.mp4.enc` (кадри
сеансу, кадр i відповідає мітці `series.t[i]`) і `session.json.enc` (метадані, виклики з часовими
мітками, ряди s_ref(t), s_enr(t), ознаки, оцінка і рішення). Тека `data/` до репозиторію не входить.

Після кожного дня запису якість перевіряється за розділом 7 протоколу збору даних:
```bash
python scripts/decrypt_recording.py data/recordings --qc
```
Записи розшифровуються лише в пам'яті, на диск нічого не пишеться. Для кожного сеансу виводяться
тип подання, інструмент підміни, цільове обличчя, освітлення, частка кадрів з обличчям (непорожні
значення `series.s_ref` після фіксації еталона) і найбільша перерва в `series.t`. Сеанс отримує
PASS, якщо обличчя є не менше ніж у 95 % кадрів і перерв понад 0,2 с немає, інакше FAIL з причиною.
Наприкінці виводиться таблиця: скільки разів кожен із 5 типів викликів траплявся в спробах кожного
учасника окремо для справжніх подань і атак; тип, що трапився менше 3 разів, позначається «(мало)».
Якщо є хоч один FAIL, скрипт завершується з кодом 1 – такі сеанси треба перезаписати.

## Віддалений запис і офлайн-атаки (без GPU)

Якщо учасники не можуть прийти до комп'ютера з прототипом, а GPU для підміни в реальному часі
немає, набір збирається в три кроки.

1. **Справжні подання вдома в учасника.** Учасник відкриває `remote/remote_recorder.html` у Chrome
   або Firefox на своєму ноутбуці. Файл можна передати будь-яким способом, інтернет для роботи
   сторінки не потрібен. Учасник:
   - вводить псевдонім, виданий дослідником (P02);
   - вибирає освітлення і кількість сеансів;
   - підтверджує згоду і виконує виклики за підказками на екрані.

   Виклики сторінка вибирає випадково, як і прототип: 3 на сеанс, тип не повторюється двічі
   поспіль. Тривалість кожного виклику 3 с, початок і кінець позначаються звуковим сигналом.
   Наприкінці сторінка дає два файли: відео `P02_<дата>.webm` і анотацію `P02_<дата>.json`
   з часовими мітками всіх вікон. Нічого не надсилається автоматично, файли учасник передає
   дослідникові сам.
2. **Однаковий шлях для обох класів.** Атаки генеруються з тих самих webm, а результат
   записується іншим кодеком. Щоб класифікатор не відрізняв атаки за кодеком чи частотою кадрів,
   справжній запис спершу проходить `generate_attacks.py` без підміни: кожен кадр входу дає
   один кадр виходу (MJPG, якість 95), а мітки часу оригіналу зберігаються поруч у
   `<відео>.times.json`.
   ```bash
   python scripts/generate_attacks.py P02_2026-11-01.webm --passthrough -o P02.avi
   ```
3. **Імпорт.** Відео проходить той самий конвеєр, що й живий сеанс (MTCNN, Face Mesh, Hands,
   MobileFaceNet), з мітками часу з `.times.json`. Виклики перевіряються тими самими класами, і
   для кожного сеансу анотації створюється `session.json.enc` у звичайному форматі, тому
   `build_dataset.py` і `decrypt_recording.py --qc` працюють без змін.
   ```bash
   python scripts/import_remote.py P02.avi P02_2026-11-01.json --delete-source
   ```
   Запис відхиляється, якщо обличчя знайдено менше ніж на 95 % кадрів поза вікнами
   викликів. З вікна реєстрації зберігається еталон `data/enrolled/P02.npy.enc`.
4. **Атаки з записів.** `scripts/generate_attacks.py` замінює обличчя учасника A на обличчя
   учасника B у кожному кадрі. Використовується модель inswapper_128 – та сама, що в
   Deep-Live-Cam (≈ 730 МБ, завантажується з Hugging Face при першому запуску). Рухи, виклики
   і часові мітки лишаються з запису A, тому підходить його анотація.
   ```bash
   python scripts/generate_attacks.py P02_2026-11-01.webm --source-video P03_2026-11-02.webm --source-annotation P03_2026-11-02.json -o P02_as_P03.avi
   python scripts/import_remote.py P02_as_P03.avi P02_2026-11-01.json --type attack --tool deep_live_cam --target P03
   ```
   Відкриті webm і згенеровані відео після імпорту треба видалити. GPU не обов'язковий:
   - на CPU цього ноутбука підміна триває ≈ 2,7 с на кадр, тобто 1–1,5 год на хвилину відео,
     запуск можна лишити у фоні на ніч; кілька паралельних процесів на 4-ядерному CPU не
     пришвидшують роботу;
   - швидше – у Google Colab з безкоштовним GPU T4: `python scripts/pack_colab.py` збирає код
     у `dist/frs-pad-colab.zip`, далі за кроками `notebooks/generate_attacks_colab.ipynb`.
     Відео в Colab можна завантажувати лише тоді, коли учасник погодився на обробку в хмарному
     сервісі (форма згоди, пункт про Google Colab).

Перевірка на парі облич з LFW: схожість ArcFace підміненого кадру з цільовою особою 0,88, з
оригіналом 0,10 (у різних людей ≈ 0).

**Відтворення через OBS для перевірки живого режиму.** ТЗ вимагає подавати атаку як потік
віртуальної камери. Готове відео можна відтворити в OBS Studio без GPU:
1. Додати джерело «Медіаджерело» з файлом `P02_as_P03.avi` і ввімкнути «Почати відтворення
   заново, коли джерело стає активним».
2. Натиснути «Запустити віртуальну камеру».
3. Запустити прототип з `--camera 1` (індекс віртуальної камери).

Виклики в такому записі не відповідають новим викликам прототипу, тому сеанс має завершитися
як «не пройдено». Це перевірка атаки повторним відтворенням, а не замінник живої підміни.

## Шифрування записів

За ТЗ (FR-65) відеозаписи і анотації набору даних зберігаються зашифрованими. Ембединги учасників
теж, бо це біометричні шаблони. `pad/storage.py` шифрує їх алгоритмом AES-256-GCM з бібліотеки
`cryptography`:

- ключ – 32 випадкові байти в base64 у змінній середовища `PAD_DATASET_KEY`; у коді, конфігурації
  і в `data/` ключ не зберігається;
- файл `.enc` – сигнатура `FRSPAD01`, випадковий nonce 12 байт і шифротекст із тегом 16 байт;
  associated data – ім'я відкритого файлу (`video.mp4`, `session.json`, `P01.npy`), тому
  перейменований, підмінений або пошкоджений файл не розшифрується;
- `video.mp4` пишеться відкритим лише під час сеансу (його потребує `cv2.VideoWriter`), після
  завершення сеансу шифрується у `video.mp4.enc` і видаляється; `session.json.enc` створюється
  одразу з пам'яті. Якщо програму закрито посеред сеансу, відео теж шифрується;
- ембединг зберігається в `data/enrolled/<псевдонім>.npy.enc`: масив записується `np.save` у
  пам'ять (`io.BytesIO`) і шифрується цілком, відкритий `.npy` не створюється. Ім'я файлу входить
  в associated data, тому ембединг P01, перейменований на `P02.npy.enc`, не розшифрується.
  Відкриті `.npy` з попередньої версії прототипу теж читаються (`--enrolled`, пошук у
  `data/enrolled/`), а після нової реєстрації того самого псевдоніма замінюються на `.npy.enc`.

Ключ створюється один раз і зберігається окремо від записів, наприклад у менеджері паролів.
Без нього записи прочитати неможливо.

```bash
python scripts/decrypt_recording.py --new-key
```

Задати ключ у PowerShell: `$env:PAD_DATASET_KEY = "<ключ>"`, у cmd: `set PAD_DATASET_KEY=<ключ>`.
Ключ потрібен `record_session.py` (без нього запис не починається), `build_dataset.py`,
`demo.py` для зашифрованих ембедингів і утиліті перегляду:

```bash
python scripts/decrypt_recording.py data/recordings
python scripts/decrypt_recording.py data/recordings/P01_bona_fide_20261017_120000 --full
python scripts/decrypt_recording.py data/recordings/P01_bona_fide_20261017_120000 -o view
```

Перша команда виводить метадані, виклики, оцінку і рішення кожного сеансу, друга – весь
`session.json`; на диск вони нічого не записують. Третя розшифровує `video.mp4` і `session.json`
у `view/<сеанс>/` для перегляду в програвачі, після перегляду цю теку треба видалити.
Ембединг так само розшифровується командою
`python scripts/decrypt_recording.py data/enrolled/P01.npy.enc -o view` (у `view/enrolled/P01.npy`).
