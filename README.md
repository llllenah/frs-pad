# FRS PAD – модуль виявлення атак підміни обличчя

Прототип модуля активного виявлення атак підміни обличчя в реальному часі для курсової роботи
«Програмне забезпечення розпізнавання обличчя у відеопотоці з виявленням атак підміни обличчя
в реальному часі на основі активних викликів». Код відповідає ТЗ (підпункт 4.2.3) і підрозділам
3.1 та 3.3 пояснювальної записки: діаграмі класів (рисунок 3.10), діаграмі станів (рисунок 3.11)
і формулам (3.1)–(3.4).

## Структура

| Клас з рисунка 3.10 | Файл | Що робить |
|---|---|---|
| `ChallengeGenerator`, `Challenge`, `OcclusionChallenge`, `HeadTurnChallenge`, `HandSwipeChallenge` | `pad/challenges.py` | випадкові виклики через `secrets.SystemRandom`, 5 типів, без двох однакових поспіль, 3 за замовчуванням |
| `ChallengeVerifier` | `pad/verifier.py` | MediaPipe Hands і Face Mesh; частка перекриття через опуклі оболонки (≥ 0,4 протягом 5 кадрів поспіль), yaw за `cv2.solvePnP` по 6 точках (\|yaw\| ≥ 30°), перетин середньої лінії обличчя центром кисті |
| `DriftFeatureExtractor`, `FeatureVector` | `pad/features.py` | s_ref, s_enr, вікна «до» 1 с, «під час» до 5 с, «після» 1,5 с; мінімум, середнє, дисперсія, найбільший стрибок і час відновлення – 26 ознак |
| `AttackClassifier`, `ThresholdClassifier`, `LogisticClassifier` | `pad/classifiers.py` | поріг на мінімумі s_ref і логістична регресія (StandardScaler + L2, `class_weight='balanced'`); оцінка сеансу – максимум оцінок викликів |
| `SessionManager`, `VerificationSession`, `SessionDecision` | `pad/session.py`, `pad/structures.py` | стани з рисунка 3.11, не більше 2 повторів, сеанс ≤ 20 с, при збої – «не пройдено» |
| `PadSettings` | `pad/settings.py`, `configs/pad.yaml` | параметри модуля і їх межі (FR-62) |

Допоміжні модулі: `pad/embedder.py` (адаптер `embed(face_crop) -> ndarray[128]`), `pad/detector.py`
(тимчасовий детектор замість MTCNN), `pad/pipeline.py` (кадр -> `FrameData`), `pad/metrics.py`
(APCER, BPCER, BPCER20, ACER, EER, AUC), `pad/dataset.py`, `pad/synthetic.py`, `pad/ui.py`, `pad/app.py`.
Веб-інтерфейс (екранні форми 4.7 і 4.8, вкладка «Моніторинг»): `pad/server.py` (FastAPI, REST і
WebSocket), `pad/web/` (односторінковий інтерфейс HTML/JS без фреймворків), `pad/identify.py`
(ідентифікація 1:N для моніторингу), `scripts/serve.py`.
Віддалений запис і офлайн-атаки: `remote/remote_recorder.html`, `pad/offline.py` (обробка відео за
анотацією), `pad/swapper.py` (inswapper_128), `scripts/import_remote.py`, `scripts/generate_attacks.py`.

Назви методів записано за PEP 8: `startSession` -> `start_session`, `onFrame` -> `on_frame`,
`isPerformed` -> `is_performed`, `headPose` -> `head_pose`, `windowStats` -> `window_stats`.

## Встановлення

Потрібен Python 3.10–3.12 (MediaPipe 0.10.21 – остання версія з `mp.solutions.hands` і `face_mesh`).

```bash
py -3.12 -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python scripts/download_models.py
```

Моделі з ТЗ – MTCNN (детекція і 5 ключових точок) і MobileFaceNet з INT8-квантуванням (ембединг 128) –
готуються з відкритих попередньо навчених ваг, без донавчання:

| Модель | Джерело ваг | Ліцензія | Файл | Розмір |
|---|---|---|---|---|
| MTCNN (P-Net, R-Net, O-Net) | [timesler/facenet-pytorch](https://github.com/timesler/facenet-pytorch), `data/*.pt` | MIT | `models/mtcnn_{pnet,rnet,onet}.onnx` | 2,0 МБ разом |
| MobileFaceNet | [foamliu/MobileFaceNet](https://github.com/foamliu/MobileFaceNet) v1.0, `mobilefacenet.pt` | Apache 2.0 | `models/mobilefacenet_int8.onnx` | 1,26 МБ (FP32 – 4,0 МБ) |

Експорт в ONNX і квантування потребують PyTorch, тому виконуються в окремому середовищі один раз:

```bash
py -3.12 -m venv .venv-export
.venv-export\Scripts\activate
pip install -r requirements.txt -r requirements-export.txt --extra-index-url https://download.pytorch.org/whl/cpu
python scripts/eval_lfw.py --download      # LFW потрібен для калібрування INT8 і перевірки точності
python scripts/export_models.py
```

`export_models.py` завантажує ваги, перевіряє SHA-256, експортує мережі в ONNX (opset 17) і
квантує MobileFaceNet статично (формат QDQ, ваги INT8 по каналах, калібрування на 300 вирівняних
обличчях LFW). Тимчасові моделі OpenCV Zoo (YuNet, SFace) з `download_models.py` лишаються
запасним варіантом: їх можна вказати в `configs/pad.yaml`.

## Тести

```bash
python -m pytest
```

200 тестів: генератор викликів, перекриття і поворот голови на синтетичних ключових точках,
ознаки на синтетичних рядах, класифікатори і показники, стани сеансу, скрипт навчання,
шифрування записів набору даних і ембедингів учасників, API веб-інтерфейсу (`tests/test_server.py`,
28 тестів: сеанс через WebSocket до рішення, перевірки форми запису, шифрування записів і еталонів,
розмітка, сумісність записів з `build_dataset.py`), моніторинг (`tests/test_monitoring.py`:
відома і невідома особа, поріг, кілька еталонів і облич, журнал подій), журнал інцидентів і перегляд
сеансу (`tests/test_review.py`: синтетичні зашифровані записи обох форматів, відбір кадрів вікна
сеансу, розшифрування лише в пам'яті), база осіб, дашборд і налаштування (`tests/test_admin.py`).
Захист сервера – `tests/test_security.py` (запити з інших сайтів, Host, розмір запитів, заголовки).
Тести API не потребують камери і моделей:
замість конвеєра кадрів у них працює синтетичний користувач.

## Демонстрація з вебкамерою

```bash
python scripts/demo.py
```

Клавіші: `E` – зареєструвати обличчя заявленої особи (30 кадрів), `S` – почати сеанс, `Q` – вихід.
У вікні: відео з точками обличчя і кисті, інструкція виклику з таймером, індикатор виконання,
графік s_ref(t) і s_enr(t), оцінки викликів, рішення, FPS і час етапів. Після виходу у `runs/`
зберігається `demo_stats_*.json` з FPS, часом етапів, витратами модуля на кадр і затримкою рішення.

Інші варіанти: `--camera 1` (наприклад, OBS Virtual Camera), `--enrolled data/enrolled/P01.npy.enc`
(потрібен ключ, розділ «Шифрування записів»), `--video file.mp4 --headless --auto-start` (без вікна,
для вимірювань).

Ключ `PAD_DATASET_KEY` для демонстрації не обов'язковий. Якщо його задано, ембединг з клавіші `E`
зберігається зашифрованим у `data/enrolled/demo.npy.enc`. Без ключа демонстрація працює як раніше,
але ембединг лишається лише в пам'яті до виходу і на диск не пишеться.

До навчання на пілотному наборі використовується базовий поріг (атака, якщо мінімум s_ref під
час виклику менший за 0,3). Це лише заглушка, поріг треба підібрати на даних.

## Веб-інтерфейс: екранні форми 4.7 і 4.8, моніторинг

```bash
$env:PAD_DATASET_KEY = "<ключ>"     # потрібен для форми запису, для верифікації – ні
python scripts/serve.py
```

Далі відкрити http://127.0.0.1:8000/ у Chrome або Edge і дозволити доступ до камери. Браузер
захоплює кадри камери (`getUserMedia`), стискає їх у JPEG і надсилає серверу через WebSocket
`/ws/stream`; сервер обробляє кадр тим самим конвеєром, що й `demo.py` (детекція, Face Mesh і Hands,
ембединг, `SessionManager`), і повертає точки, стан сеансу, ряди s_ref(t), s_enr(t), ознаки, оцінку
і рішення. Наступний кадр надсилається після відповіді на попередній, тому частота кадрів
дорівнює частоті обробки. Сервер слухає лише 127.0.0.1: браузер дозволяє камеру на localhost без
HTTPS, а біометричний відеопотік не виходить за межі комп'ютера. Інші параметри: `--port 8080`,
`--classifier models/pad_logistic.json`, `--data data` (тека з `enrolled/` і `recordings/`).

**Сеанс верифікації (рисунок 4.7, вкладка «Верифікація»).** Ліворуч – заявлена особа (псевдонім),
стан еталона, номер сеансу, список випадкових викликів (виконано, поточний, не виконано) і блок
«Перевірка виконання» (кількість точок Face Mesh і Hands, кути yaw і pitch, упевненість детекції).
У центрі – відео з камери (віддзеркалене) з рамкою обличчя, підписом «P01? 0,98» (поточна s_enr),
точками Face Mesh і кистю, інструкція виклику з номером, індикатор виконання, круговий таймер і
рядок з вимірюванням (частка перекриття і сторона, кут повороту або зміщення кисті); під відео –
графік s_ref(t) і s_enr(t) з вікнами «до», «під час» і «після». Праворуч – рішення (до кінця
сеансу – попередня оцінка за вже виконаними викликами), ознаки дрейфу останнього виконаного
виклику (усі 26 – у розгорнутому списку), швидкодія і кнопки «Повторити» / «Почати сеанс»
(«Завершити» під час сеансу). Еталон реєструється кнопкою «Зареєструвати еталон» (30 кадрів, як
клавіша `E` у `demo.py`) або «З фото» (наприклад, цільове обличчя). З ключем еталон зберігається
у `data/enrolled/<псевдонім>.npy.enc`, без ключа – лише в пам'яті сервера до його зупинки.

**Запис сеансів для набору даних (рисунок 4.8, вкладка «Дослідження»).** Параметри сеансу:
учасник (лише псевдонім), модель камери, освітлення, обов'язкова позначка про письмову згоду
(з номером), тип подання, інструмент підміни і цільове обличчя (для атаки), джерело відео,
кількість і тривалість викликів, набір типів викликів (не менше 4). Кнопка «Почати запис» доступна
лише за наявності згоди, ключа і камери; сервер ще раз перевіряє ці умови. Попередній перегляд за
замовчуванням розмитий («приховати обличчя»), під час запису на ньому видно інструкцію і таймер.
Записи зберігаються так само, як у `record_session.py`: `data/recordings/<псевдонім>_<тип>_<час>/`
з `video.mp4.enc` і `session.json.enc` (метадані, сценарій, умови, виклики, ряди, ознаки, рішення);
`build_dataset.py` читає їх без змін. Якщо сеанс перервано (кнопка або закриття вкладки),
зберігається лише зашифроване відео. Таблиця «Записані сеанси» розшифровує анотації в пам'яті і
показує тип, інструмент, ціль, виклики (ЛП, ПП, Р, ПГ-Л, ПГ-П, ПР), умови, тривалість і статус;
клік по статусу «Очікує перевірки» позначає сеанс розміченим (`annotation.reviewed` у
`session.json.enc`). Ліворуч – підсумок набору даних. У таблиці є і сеанси імпортованих записів
(підтеки `<запис>_sNN`, позначка «с1», «с2» біля псевдоніма). Кнопка «Переглянути» відкриває
перегляд сеансу (нижче).

**Перегляд сеансу.** Відео сеансу з графіком s_ref(t), s_enr(t) під ним: вертикальна лінія на
графіку рухається разом з відео, вікна викликів затінено і підписано (номер, назва, ✓ або ×),
вікна «до» і «після» – світліші, невиконаний виклик заштриховано. Клік по графіку або по виклику
в списку ліворуч – перехід до цього моменту; кнопки «Відтворити» / «Пауза» (пробіл), повзунок,
швидкість 0,5× і 1×. Над відео – поточний виклик і значення s_ref, s_enr. Праворуч – рішення,
оцінка і поріг, мітка набору даних (справжнє подання чи атака) і чи збігається з нею рішення.
Браузер не відтворює mp4v і AVI (MJPG), тому сервер розшифровує відео лише в пам'яті
(`storage.read_encrypted_buffer`, потоково, тег GCM перевіряється до декодування), декодує OpenCV
(FFmpeg читає з буфера в пам'яті) тільки кадри потрібного сеансу, зменшує їх до 640 пікселів
завширшки (JPEG, якість 75) і тримає в кеші на 4 сеанси (`pad/review.py`). Кадри віддаються з
`Cache-Control: no-store`, у браузері лишаються в пам'яті сторінки; на диск нічого не пишеться.
Для живих записів кадр i відповідає `series.t[i]`, для імпортованих – кадри відбираються за
`frame_times.json.enc` у вікні сеансу від `explanation.t0`. Записи, імпортовані офлайн, мають
рішення `offline` без оцінки: перегляд показує, які виклики виконано, і «оцінка не обчислювалася
під час запису»; якщо сервер запущено з навченою моделлю (`models/pad_logistic.json`), ознаки
обчислюються з рядів і показується «оцінка поточною моделлю». Без ключа `PAD_DATASET_KEY` перегляд
записів недоступний (про це видно повідомлення). Завершені сеанси перевірки з вкладки
«Верифікація» теж можна переглянути: їх кадри (до ≈ 20 кадр/с, зменшені) тримаються лише в
пам'яті сервера для 5 останніх сеансів і ключа не потребують.

**Сповіщення і журнал інцидентів.** Коли моніторинг підтверджує невідому особу або перевірка
завершується рішенням «атака», зверху з'являється червоне сповіщення зі знімком обличчя і коротким
звуковим сигналом (WebAudio, без файлів); «не пройдено» – жовтогаряче, «справжнє подання» –
спокійне зелене, яке зникає саме. Червоне і жовтогаряче тримаються до кнопки «Прийнято». Кнопка
«Звук» у верхній панелі вимикає сигнали (вибір запам'ятовується в браузері). Сповіщення
показується один раз на подію журналу, тобто з тим самим усуненням повторів, що й журнал
моніторингу. Журнал інцидентів (вкладка «Моніторинг», праворуч) об'єднує появу осіб і результати
перевірок: знімок, час, псевдонім або «невідома особа», подібність або оцінка атаки, рішення;
позначка «лише тривоги» ховає появу відомих осіб. Клік по рядку – подробиці зі збільшеним знімком і
кнопкою «Переглянути сеанс» для перевірок. Знімки (обличчя з запасом 25 %, висота 112 пікселів)
зберігаються лише в пам'яті сервера, останні 50, і зникають після перезапуску.

**Дашборд, база осіб, налаштування.** «Дашборд» – огляд за сьогодні: скільки разів з'являлися
відомі і невідомі особи, скільки перевірок пройдено, атак виявлено і не пройдено (лічильники
сервера з моменту запуску, без вигаданих чисел), останні тривоги, FPS, кількість осіб у базі.
«База осіб» (форма 4.3) – список еталонів (псевдонім, як зберігається, дата реєстрації), пошук,
додавання з фото або з камери (30 кадрів), видалення з підтвердженням (файл
`data/enrolled/<псевдонім>.npy.enc` і пам'ять сервера). «Налаштування» – поточні параметри модуля,
розпізнавання і захисту даних; пороги розпізнавання і атаки можна змінити, але лише в пам'яті до
перезапуску сервера (постійні значення – `configs/pad.yaml`).

**Моніторинг (вкладка «Моніторинг»).** Сценарій: охоронна компанія реєструє еталони працівників,
охоронець дивиться потік камери. Кожне обличчя в кадрі (до 5, упевненість MTCNN ≥ 0,9)
порівнюється з еталонами всіх осіб з `data/enrolled/*.npy.enc` (потрібен ключ) і з еталонами в
пам'яті сервера; подібність косинусна, пошук – FAISS `IndexFlatIP`, якщо встановлено `faiss`,
інакше numpy (для бази прототипу це той самий точний перебір; індекс IVF з ТЗ – для повної системи
в дипломному проєкті). Відоме обличчя – зелена рамка з псевдонімом і подібністю, невідоме –
червона рамка і сповіщення «Невідома особа». Праворуч – обличчя в кадрі і журнал інцидентів (час,
псевдонім або «невідома», подібність, знімок); подія пишеться, коли особу розпізнано 3 кадри поспіль, і
повторюється, лише якщо її не було в кадрі понад 10 с. Кнопка «Перевірити» біля відомої особи
відкриває вкладку «Верифікація» і запускає сеанс з активними викликами для цієї особи: так модуль
виявлення атак захищає розпізнавання від підміни обличчя в реальному часі. Рішення кожного сеансу перевірки
теж потрапляє в журнал. Поріг 0,5 і інші параметри – ключ `monitoring` у
`configs/pad.yaml` (на LFW поріг верифікації 1:1 ≈ 0,30, для 1:N узято з запасом; на записах
учасників його ще треба перевірити). Моніторинг використовує той самий WebSocket, що й інші
вкладки: команда `monitor` перемикає з'єднання в режим ідентифікації, Face Mesh і Hands у цьому
режимі не запускаються.

REST: `GET /api/config`, `GET /api/participants`, `POST /api/participants/{id}/image`,
`POST /api/sessions`, `GET /api/sessions/{id}`, `POST /api/sessions/{id}/cancel`,
`GET /api/recordings`, `POST /api/recordings/{name}/review`, `GET /api/stats`, `GET /api/monitor`
(база еталонів і журнал моніторингу), `GET /api/incidents`, `GET /api/incidents/{id}/snapshot.jpg`,
`GET /api/review/{uid}` (ряди, виклики, рішення, мітки часу кадрів; uid – ім'я теки сеансу або код
сеансу перевірки `VS-…`), `GET /api/review/{uid}/frame/{i}.jpg`, `GET /api/persons`,
`DELETE /api/persons/{id}`, `GET /api/dashboard`, `GET /api/settings`, `PUT /api/settings`;
опис запитів – на http://127.0.0.1:8000/docs. WebSocket
`/ws/stream`: текстові команди `attach`, `enroll` і `monitor` (`{"cmd": "monitor", "on": true}` –
ідентифікація 1:N, база еталонів перечитується), двійкові повідомлення – 8 байт часу кадру
(float64) і JPEG. `POST /api/sessions` приймає `"origin": "monitor"` для перевірки, запущеної з
моніторингу.

Скріншоти обох форм – у `docs/`: `form_4_7_verification.png` (виконання виклику),
`form_4_7_result.png` (рішення), `form_4_8_recording.png` (запис), `form_4_8_records.png`
(таблиця записів). Їх знято в Edge з фальшивою камерою, на яку подавалося тестове відео з
портретом (не вебкамера). Портрет не може виконати виклик, тому сеанси на скріншотах завершуються
рішенням «не пройдено», а FPS нижчий, ніж у вимірюваннях нижче (браузер і сервер працювали на
одному завантаженому ноутбуці). Для розділу 5 записки скріншоти краще перезняти з вебкамерою,
виконавши виклики.

## Запис пілотного набору

Учасники позначаються лише псевдонімами (P01, P02, …), запис без письмової згоди скрипт не
запускає. Цільові обличчя для атак – обличчя учасників за згодою або синтетичні. Записи
зберігаються лише зашифрованими (розділ «Шифрування записів»), тому перед записом треба задати
ключ у `PAD_DATASET_KEY`.

1. Реєстрація учасника: запустити запис і натиснути `E`, ембединг збережеться зашифрованим у
   `data/enrolled/P01.npy.enc`.
2. Справжні подання (наприклад, 10 сеансів, кожен починається клавішею `S`):
   ```bash
   python scripts/record_session.py --participant P01 --consent --type bona_fide --claimed P01
   ```
3. Атаки: у Deep-Live-Cam або DeepFaceLive вибрати цільове обличчя T01, вивести результат у
   OBS Studio і ввімкнути віртуальну камеру. Заявлена особа – ціль, тому її ембединг береться з
   фото цілі або з раніше збереженого `data/enrolled/T01.npy.enc` (не натискати `E` на підміненому потоці):
   ```bash
   python scripts/record_session.py --participant P01 --consent --type attack --tool deep_live_cam --target T01 --claimed T01 --enroll-image targets/T01.jpg --camera 1
   ```
   Індекс віртуальної камери залежить від системи (зазвичай 1 або 2).
4. Додатково можна вказати умови: `--lighting low --webcam-model "Logitech C270"`.

Кожен сеанс зберігається в `data/recordings/<псевдонім>_<тип>_<час>/`: `video.mp4.enc` (кадри
сеансу, кадр i відповідає мітці `series.t[i]`) і `session.json.enc` (метадані, виклики з часовими
мітками, ряди s_ref(t), s_enr(t), ознаки, оцінка і рішення). Тека `data/` до репозиторію не входить.

Після кожного дня запису якість перевіряється за розділом 7 протоколу збору даних:
```bash
python scripts/decrypt_recording.py data/recordings --qc
```
Записи розшифровуються лише в пам'яті, на диск нічого не пишеться. Для кожного сеансу виводяться
тип подання, інструмент підміни, цільове обличчя, освітлення, частка кадрів з обличчям (непорожні
значення `series.s_ref` після фіксації еталона) і найбільша перерва в `series.t`. Сеанс отримує
PASS, якщо обличчя є не менше ніж у 95 % кадрів і перерв понад 0,2 с немає, інакше FAIL з причиною.
Наприкінці виводиться таблиця: скільки разів кожен із 5 типів викликів траплявся в спробах кожного
учасника окремо для справжніх подань і атак; тип, що трапився менше 3 разів, позначається «(мало)».
Якщо є хоч один FAIL, скрипт завершується з кодом 1 – такі сеанси треба перезаписати.

## Віддалений запис і офлайн-атаки (без GPU)

Якщо учасники не можуть прийти до комп'ютера з прототипом, а GPU для підміни в реальному часі
немає, набір збирається в три кроки.

1. **Справжні подання вдома в учасника.** Учасник відкриває `remote/remote_recorder.html` у Chrome
   або Firefox на своєму ноутбуці. Файл можна передати будь-яким способом, інтернет для роботи
   сторінки не потрібен. Учасник:
   - вводить псевдонім, виданий дослідником (P02);
   - вибирає освітлення і кількість сеансів;
   - підтверджує згоду і виконує виклики за підказками на екрані.

   Виклики сторінка вибирає випадково, як і прототип: 3 на сеанс, тип не повторюється двічі
   поспіль. Тривалість кожного виклику 3 с, початок і кінець позначаються звуковим сигналом.
   Наприкінці сторінка дає два файли: відео `P02_<дата>.webm` і анотацію `P02_<дата>.json`
   з часовими мітками всіх вікон. Нічого не надсилається автоматично, файли учасник передає
   дослідникові сам.
2. **Однаковий шлях для обох класів.** Атаки генеруються з тих самих webm, а результат
   записується іншим кодеком. Щоб класифікатор не відрізняв атаки за кодеком чи частотою кадрів,
   справжній запис спершу проходить `generate_attacks.py` без підміни: кожен кадр входу дає
   один кадр виходу (MJPG, якість 95), а мітки часу оригіналу зберігаються поруч у
   `<відео>.times.json`.
   ```bash
   python scripts/generate_attacks.py P02_2026-11-01.webm --passthrough -o P02.avi
   ```
3. **Імпорт.** Відео проходить той самий конвеєр, що й живий сеанс (MTCNN, Face Mesh, Hands,
   MobileFaceNet), з мітками часу з `.times.json`. Виклики перевіряються тими самими класами, і
   для кожного сеансу анотації створюється `session.json.enc` у звичайному форматі, тому
   `build_dataset.py` і `decrypt_recording.py --qc` працюють без змін.
   ```bash
   python scripts/import_remote.py P02.avi P02_2026-11-01.json --delete-source
   ```
   Запис відхиляється, якщо обличчя знайдено менше ніж на 95 % кадрів поза вікнами
   викликів. З вікна реєстрації зберігається еталон `data/enrolled/P02.npy.enc`.
4. **Атаки з записів.** `scripts/generate_attacks.py` замінює обличчя учасника A на обличчя
   учасника B у кожному кадрі. Використовується модель inswapper_128 – та сама, що в
   Deep-Live-Cam (≈ 730 МБ, завантажується з Hugging Face при першому запуску). Рухи, виклики
   і часові мітки лишаються з запису A, тому підходить його анотація.
   ```bash
   python scripts/generate_attacks.py P02_2026-11-01.webm --source-video P03_2026-11-02.webm --source-annotation P03_2026-11-02.json -o P02_as_P03.avi
   python scripts/import_remote.py P02_as_P03.avi P02_2026-11-01.json --type attack --tool deep_live_cam --target P03
   ```
   Відкриті webm і згенеровані відео після імпорту треба видалити. GPU не обов'язковий:
   - на CPU цього ноутбука підміна триває ≈ 2,7 с на кадр, тобто 1–1,5 год на хвилину відео,
     запуск можна лишити у фоні на ніч; кілька паралельних процесів на 4-ядерному CPU не
     пришвидшують роботу;
   - швидше – у Google Colab з безкоштовним GPU T4: `python scripts/pack_colab.py` збирає код
     у `dist/frs-pad-colab.zip`, далі за кроками `notebooks/generate_attacks_colab.ipynb`.
     Відео в Colab можна завантажувати лише тоді, коли учасник погодився на обробку в хмарному
     сервісі (форма згоди, пункт про Google Colab).

Перевірка на парі облич з LFW: схожість ArcFace підміненого кадру з цільовою особою 0,88, з
оригіналом 0,10 (у різних людей ≈ 0).

**Відтворення через OBS для перевірки живого режиму.** ТЗ вимагає подавати атаку як потік
віртуальної камери. Готове відео можна відтворити в OBS Studio без GPU:
1. Додати джерело «Медіаджерело» з файлом `P02_as_P03.avi` і ввімкнути «Почати відтворення
   заново, коли джерело стає активним».
2. Натиснути «Запустити віртуальну камеру».
3. Запустити прототип з `--camera 1` (індекс віртуальної камери).

Виклики в такому записі не відповідають новим викликам прототипу, тому сеанс має завершитися
як «не пройдено». Це перевірка атаки повторним відтворенням, а не замінник живої підміни.

## Результати пілотного набору

4 учасники (P01–P04), 34 справжні сеанси і 34 атаки, згенеровані офлайн моделлю inswapper_128 з
тих самих записів (`generate_attacks.py`), обидва класи пройшли однаковий шлях обробки. Перехресна
перевірка з виключенням учасника; атаки з обличчям тестового учасника як цільовим у навчання не
потрапляють. Повні числа – `runs/pilot_report/summary.json`, `python scripts/analyze_pilot.py`.

| Модель (рівень сеансу) | APCER | BPCER | EER | AUC |
|---|---|---|---|---|
| Логістична регресія, 26 ознак | 0,0 % | 2,9 % | 0,0 % | 1,000 |
| Логістична регресія, лише s_ref | 48,5 % | 29,4 % | 24,2 % | 0,783 |
| Поріг на мінімумі s_ref | 57,6 % | 38,2 % | 51,5 % | 0,479 |

Абляція: ознаки лише вікна «до» виклику дають AUC 0,997, тобто атаки цього генератора видно ще до
виклику (підмінене обличчя стабільніше і менше схоже на заявлену особу), і внесок активних викликів на
пілотному наборі не підтверджено. Генератор продовжує підміну навіть під рукою, тому провал
подібності під час перекриття трапляється рідко. Обмеження: малий набір, офлайн-атаки одного
генератора з детектором MTCNN замість RetinaFace, еталони осіб з того самого запису, правила перевірки
викликів і контролю якості уточнено після перших записів. Найслабший виклик – «провести рукою»
(8 з 23 виконано).

## Захист сервера

- Сервер слухає лише 127.0.0.1 і приймає тільки запити з власною адресою в заголовку Host
  (захист від DNS rebinding); на іншій адресі `serve.py` виводить попередження.
- POST, PUT, DELETE і WebSocket відхиляються, якщо Origin або Sec-Fetch-Site вказують на інший сайт:
  сторінка стороннього сайту в браузері оператора не може додати обличчя, видалити особу,
  змінити пороги чи підключитися до відеопотоку.
- Фото – до 10 МБ і лише зображення, кадр WebSocket – до 8 МБ; псевдоніми й ідентифікатори
  записів перевіряються регулярними виразами (вихід за межі каталогу даних неможливий).
- Заголовки X-Frame-Options: DENY, CSP frame-ancestors 'none', nosniff, no-referrer.
- Записи, анотації й еталони – AES-256-GCM (розділ «Шифрування записів»), знімки журналу
  інцидентів – лише в пам'яті. Перевірки – `tests/test_security.py`.

## Шифрування записів

За ТЗ (FR-65) відеозаписи і анотації набору даних зберігаються зашифрованими. Ембединги учасників
теж, бо це біометричні шаблони. `pad/storage.py` шифрує їх алгоритмом AES-256-GCM з бібліотеки
`cryptography`:

- ключ – 32 випадкові байти в base64 у змінній середовища `PAD_DATASET_KEY`; у коді, конфігурації
  і в `data/` ключ не зберігається;
- файл `.enc` – сигнатура `FRSPAD01`, випадковий nonce 12 байт і шифротекст із тегом 16 байт;
  associated data – ім'я відкритого файлу (`video.mp4`, `session.json`, `P01.npy`), тому
  перейменований, підмінений або пошкоджений файл не розшифрується;
- `video.mp4` пишеться відкритим лише під час сеансу (його потребує `cv2.VideoWriter`), після
  завершення сеансу шифрується у `video.mp4.enc` і видаляється; `session.json.enc` створюється
  одразу з пам'яті. Якщо програму закрито посеред сеансу, відео теж шифрується;
- ембединг зберігається в `data/enrolled/<псевдонім>.npy.enc`: масив записується `np.save` у
  пам'ять (`io.BytesIO`) і шифрується цілком, відкритий `.npy` не створюється. Ім'я файлу входить
  в associated data, тому ембединг P01, перейменований на `P02.npy.enc`, не розшифрується.
  Відкриті `.npy` з попередньої версії прототипу теж читаються (`--enrolled`, пошук у
  `data/enrolled/`), а після нової реєстрації того самого псевдоніма замінюються на `.npy.enc`.

Ключ створюється один раз і зберігається окремо від записів, наприклад у менеджері паролів.
Без нього записи прочитати неможливо.

```bash
python scripts/decrypt_recording.py --new-key
```

Задати ключ у PowerShell: `$env:PAD_DATASET_KEY = "<ключ>"`, у cmd: `set PAD_DATASET_KEY=<ключ>`.
Ключ потрібен `record_session.py` (без нього запис не починається), `build_dataset.py`,
`demo.py` для зашифрованих ембедингів і утиліті перегляду:

```bash
python scripts/decrypt_recording.py data/recordings
python scripts/decrypt_recording.py data/recordings/P01_bona_fide_20261017_120000 --full
python scripts/decrypt_recording.py data/recordings/P01_bona_fide_20261017_120000 -o view
```

Перша команда виводить метадані, виклики, оцінку і рішення кожного сеансу, друга – весь
`session.json`; на диск вони нічого не записують. Третя розшифровує `video.mp4` і `session.json`
у `view/<сеанс>/` для перегляду в програвачі, після перегляду цю теку треба видалити.
Ембединг так само розшифровується командою
`python scripts/decrypt_recording.py data/enrolled/P01.npy.enc -o view` (у `view/enrolled/P01.npy`).

## Навчання і оцінювання

```bash
python scripts/build_dataset.py data/recordings -o data/features.csv
python scripts/train.py --data data/features.csv --install
```

`build_dataset.py` заново обчислює 26 ознак кожного виконаного виклику з рядів у `session.json.enc`
(відкриті `session.json` теж читаються).
`train.py` порівнює `ThresholdClassifier` і `LogisticClassifier` перехресною перевіркою
leave-one-subject-out: для кожного учасника модель навчається на інших, поріг τ підбирається на
внутрішній перевірці так, щоб BPCER не перевищував 5 % (`target_bpcer` у
`configs/experiment_pilot.yaml`). Результати в `runs/train_<час>/`:

- `metrics.json` – APCER (для кожного інструмента і найбільший), BPCER, ACER, BPCER20, EER, AUC на
  рівні сеансу, EER і AUC на рівні викликів і для кожного типу виклику, ваги ознак;
- `folds.csv`, `session_scores.csv` – показники по фолдах і оцінки сеансів;
- `det.png`, `roc.png` – DET- і ROC-криві;
- `model_logistic.json`, `model_logistic.onnx`, `model_threshold.json` – моделі на всіх даних з
  рекомендованим порогом `recommended_threshold`.

`--install` копіює модель у `models/pad_logistic.json`; рекомендований поріг треба перенести в
`threshold` у `configs/pad.yaml`.

Перевірка скрипта без пілотного набору: `python scripts/train.py --synthetic`. Синтетичні ряди
лише імітують якісну різницю з підрозділу 3.3, тому їх показники не є результатом роботи.

## Точність розпізнавання на LFW

`python scripts/eval_lfw.py` – стандартні 6000 пар LFW, 10-кратна перехресна перевірка, MTCNN для
вирівнювання (обличчя знайдено на всіх 7701 зображеннях пар). Результати – у `runs/lfw_*.json`.

| Модель | Розмір | Точність LFW | Час ембединга (CPU) |
|---|---|---|---|
| MobileFaceNet INT8 (основна) | 1,26 МБ | 99,30 % ± 0,41 % | 2,5 мс |
| MobileFaceNet FP32 | 4,0 МБ | 99,42 % ± 0,37 % | 3,9 мс |

Автор ваг повідомляє 99,48 % для FP32. Квантування знижує точність на 0,12 відсоткового пункта і
прискорює ембединг у 1,5 раза. MTCNN на кадрі 1280 × 720 (масштабування до 640 пікселів,
мінімальне обличчя 20 пікселів) – 38 мс; з налаштуваннями прототипу (мінімальне обличчя 40) – 19 мс.

## Виміряна швидкодія (ноутбук, Intel Core i5-8265U, без GPU)

З MTCNN і MobileFaceNet INT8 конвеєр кадру 1280 × 720 з обличчям (детекція, Face Mesh, ембединг)
обробляє 28 кадрів/с: детекція 19 мс, Face Mesh 13 мс, ембединг 3,6 мс у середньому.
Нижче – вимірювання попередньої версії з тимчасовими моделями.

Вимірювання на відеофайлі 1280 × 720 з портретом (`demo.py --video ... --headless --auto-start`):
Hands увімкнено під час викликів, але кисті в кадрі немає, тобто це найгірший випадок для Hands.
Повторити вимірювання на вебкамері з живою людиною ще треба.

| Показник | Значення |
|---|---|
| Частота обробки кадрів | 23–25 FPS |
| Детекція YuNet / ембединг SFace / MediaPipe (Face Mesh + Hands) – тимчасові моделі | 9 / 15 / 16 мс у середньому |
| Витрати модуля виявлення атак на кадр (MediaPipe + SessionManager) | 16 мс у середньому, 35 мс p95 |
| Обчислення ознак і класифікація на останньому кадрі | 2–4 мс (сама класифікація – 0,1 мс) |

Найдорожча частина – пошук долоні в Hands, коли кисті ще немає в кадрі, тому Hands запускається
лише під час викликів з кистю. i5-8265U слабший за мінімальну конфігурацію з ТЗ (i5-8400).

## Обмеження прототипу

- Офлайн-атаки відрізняються від живої підміни: немає затримки обробки і пропусків кадрів, які
  дає Deep-Live-Cam на слабкому GPU, тому ознаки, пов'язані з часом відновлення, у них можуть
  бути чистішими. Крім того, кожен виклик у віддаленому записі триває рівно 3 с, а в живому
  сеансі він завершується одразу після виконання. Тому модель, навчену лише на віддалених
  записах, треба перевірити хоча б на кількох живих сеансах.
- Підміна визначає обличчя детектором MTCNN з порогом 0,9. Кадр, де обличчя закрите сильніше,
  лишається без підміни, як і в Deep-Live-Cam.
- Рішення формується через 1,5 с після завершення останнього виклику, бо стільки триває вікно
  «після». Вимога ТЗ «не пізніше 1 с» виконується лише для самого обчислення (кілька мілісекунд);
  щоб виконати її буквально, треба скоротити вікно «після» або вважати його частиною виклику.
- Обмеження 20 с діє на одну спробу: після невиконаного виклику спроба повторюється з новим
  набором викликів (номер спроби – `attempt_no`), еталон зберігається.
- Відео набору пишеться кодеком mp4v замість H.264.
- Відкритий `video.mp4` видаляється звичайним видаленням файлу без перезапису вмісту, тож на
  диску його залишки можна відновити. Так само видаляється відкритий `.npy` попередньої реєстрації,
  коли його замінює `.npy.enc`.
- Поріг перекриття 0,4 від площі всього обличчя для «закрити рот і підборіддя» може виявитися
  жорстким, його варто перевірити на перших записах.
- Веб-інтерфейс розрахований на одного оператора: сервер обробляє кадри по одному, а кадр для
  запису проходить стиснення JPEG у браузері (якість 0,9) перед кодуванням у mp4v.
- У неактивній вкладці браузер призупиняє надсилання кадрів; після повернення на вкладку сеанс
  завершується як «не пройдено», бо час між кадрами перевищує обмеження 20 с.
- SFace INT8 (`download_models.py --int8`) у ONNX Runtime працює в 6–8 разів повільніше за FP32,
  тому серед запасних моделей використовується FP32 (MobileFaceNet INT8, навпаки, швидша за FP32).
- Вимірювання з MTCNN і MobileFaceNet зроблено на кадрі з фотографією обличчя; на вебкамері з живою
  людиною їх ще треба повторити.
